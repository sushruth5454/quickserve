## Scope & method

**Scope:** venue discovery, venue details, slot availability, date/time/duration, participants and capacity, the three booking models (instant + online, request → approval → pay, pay-at-venue), payment, cancellation, refunds, payouts, booking history, the venue-operator console, and admin sports tooling.

**Method:**
1. I read the latest definition of every sports SQL function. Later migrations override earlier ones, so: `0058_sports_payments.sql` for `save_sports_venue`, `save_sports_resource`, `get_sports_slots`, `request_sports_slot`, `book_sports_slot`, `decide_sports_booking`, `prepare_sports_payment`, `_queue_sports_refund`, `_refund_unmatched_sports_capture`, `record_sports_payment_paid`, `cancel_sports_booking`, `_create_sports_payout`, `expire_sports_requests`, `claim_due_transfers`, and the read RPCs. `0048_sports.sql` is still the latest for `set_sports_hours`, `save_sports_price_rule`, `add_sports_block`, `remove_sports_block`, `submit_sports_venue`, `admin_set_venue_status` and `search_sports_venues`. `0053_activity_contracts.sql` is the latest for `list_my_customer_sports_bookings`. `0054`/`0055` hold the sports flags and rules (`_sports_feature`, `_sports_rule`, the `sports_rules` defaults). `0001_init.sql:642` holds `_queue_refund`.
2. I read the edge functions `create-payment/{index,logic}.ts`, `verify-payment/index.ts`, `razorpay-webhook/index.ts` and `_shared/record-payment.ts`.
3. I read the app code: `app/app/sports/{index,[activity],bookings,manage}.tsx`, `app/app/sports-booking/[id].tsx`, `app/app/sports-checkout/[id].tsx`, `app/app/admin/sports.tsx`, `app/src/features/sports/{api,model,SportsVenueBookingScreen}.ts(x)`, and the sports segment of `app/src/features/activity/UnifiedActivityScreen.tsx`.
4. I compared the code with the plan in doc 12 (§1 R5–R7, §6, §8, §11, §12).
5. CI evidence:
   - Backend run `44358292571`: `sports.test.mjs` and `sports_payments.test.mjs` PASS. The "Verify scheduled-job prerequisites" step logs `pg_cron is enabled` and `sports-booking-expiry: */5 * * * *`.
   - App run `44365580862`, "Typecheck and unit tests": `src/features/sports/__tests__/model.test.ts` and `venueSettings.test.ts` PASS (27 suites, 246 tests).
   - E2E run `44365580570`: `phase-6-sports-booking-request` and `my-activity-sports-segment` FAILED (log lines 726–727 and 796–797).
6. The SQL tests run on **PGlite**, a single in-process connection (CI step name "SQL tests (PGlite)"). Their "race" checks therefore run the calls one after another. They do not exercise real lock contention.

**Headline:**
- The SQL backend for the three payment models is largely correct and well tested: holds, expiry, idempotency, late/duplicate/mismatched captures, the 100/50/0 % refunds, and payouts on completion.
- **The app is not wired to the real payment path.** `createSportsPayment` sends `sportsBookingId`, but the edge function requires `booking_id`, so every online payment attempt is rejected with HTTP 400.
- The customer list views (booking list and My Activity) **show wrong payment status, amount and deadline**.
- A venue **never receives its share when a customer cancels late** (the non-refunded money).
- Both sports E2E steps fail. One test uses selectors that no longer exist in the app; the other fails as a knock-on effect.
- Doc 12's F2 ("wire sports UI to real payments") and G2 ("venue calendar/earnings") are confirmed **not built**.

## Persona walkthroughs (code-based, not real-user tested)

### P1 — Customer booking a badminton court for two hours
1. **Discover.** Home → "Sports & venues" (`sports/index.tsx`) → taps Badminton. The search uses the selected location and a fixed 15 km radius (`[activity].tsx:36-41`). The list shows distance, "From ₹X" and a VERIFIED badge. There is no filter by date, time or availability.
2. **Venue.** `/venue/[id]` renders `SportsVenueBookingScreen`: photos, address and amenities. There are no prices up front and no cancellation policy. The customer picks "Badminton · Court 1".
3. **Date.** Defaults to tomorrow. Today/Tomorrow/Next day buttons, or free text `YYYY-MM-DD`. A badly formatted date shows a raw server error.
4. **Time and 2 hours.** Free slots appear as chips with "₹X / slot"; taken and blocked slots are hidden.
   - **If `sports_multi_slot` is OFF (the default, 0054:18):** there is no Duration control and the server rejects `p_slots > 1`. A 60-minute court cannot be booked for 2 hours in one booking. The workaround is two separate bookings, each with its own hold.
   - **If it is ON:** the customer picks "2 slots" (not "2 hours"). No total price is shown before booking.
5. **Payment choice.**
   - **Online flag OFF (default):** pay at venue only. With the default `approval` mode the button says "Send request" → status `requested` → toast "Request sent" → booking detail shows "Waiting for venue" and the request expiry (≤ 2 h).
   - **Instant + online:** `pending_payment` with a 10-minute hold → checkout countdown → "Pay ₹X" → **400 "sports booking_id is required"** (WS4-01). The hold expires and the booking ends `expired`. The customer can never pay.
   - **Approval + online:** after the venue accepts, `awaiting_payment`. Detail and checkout show the correct `pay_by`, but **the list shows a stale deadline** (WS4-02). Paying fails as above.
6. **History.**
   - `sports/bookings.tsx` shows the status labels correctly, but the payment summary falls back to "Pay at venue" for every accepted booking, including paid-online ones (WS4-02).
   - My Activity → Sports shows raw `ACCEPTED`/`PENDING_PAYMENT` and "Pay at venue"/"No online payment".
7. **Cancel.** One tap on "Cancel booking" with no confirmation and no refund amount shown. The server applies 100 % (≥ 24 h), 50 % of price (≥ 6 h) or 0 %. The fee is never refunded on a customer cancellation.

**Verdict:** the pay-at-venue request flow works end to end in code. The online flow cannot be completed. A two-hour booking needs a switch that is OFF by default, and the customer sees neither a total nor the policy before committing.

### P2 — Sports venue operator managing availability and reservations
1. **Entry.** Sports home shows "My venues" only when the active role is `provider` (`sports/index.tsx:60`). Another route is `merchant-work` → "Open sports bookings".
2. **Set up.** Create the venue with name, address, city/area and **manually typed latitude/longitude**, comma-separated amenities, and photo URLs typed one per line. Add a court: activity, name, slot length as free text (30/60/90/120), booking mode (only if the instant flag is on) and capacity (only if the capacity flag is on). Set hours per weekday for the **whole venue** (cannot cross midnight). Add a price rule. Submit for verification; an admin verifies.
3. **Change prices.** Not possible. A new rule for the same window is rejected as overlapping, and there is no edit or delete (WS4-09).
4. **Block time.** Possible, but a block can be placed on a slot a customer is paying for, and the payment then confirms inside the block (WS4-05). Blocks can be removed.
5. **Requests.** A notification links to `/sports-booking/[id]`. The owner must accept or decline before `min(start − 30 min, created + 2 h)`; declining needs a reason of at least 3 characters. Managers cannot act (WS4-28).
6. **Reservations.** **The owner has no list of confirmed or paid bookings**, only pending requests (`manage.tsx:368`). There is no calendar, no customer contact and no earnings/payout view (G2 not built). Cancelling a confirmed booking needs the notification deep link and a reason; the customer gets a 100 % refund.
7. **Money.** Online payouts are created only when a booking completes: price − refund − commission − 18 % GST on commission, released after 24 h. Retained money from late customer cancellations never reaches the venue (WS4-03). Editing any venue detail delists the venue until it is re-verified (WS4-21).

**Verdict:** the operator can set up and respond to requests. Running a day of reservations, correcting prices and seeing earnings are not supported.
