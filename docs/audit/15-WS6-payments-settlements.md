## Scope & method

**Scope.** Every money path for home services (`inspect_quote`, `fixed` packages and add-ons, `time_based` sessions and packs), recurring visits (0057), sports (0058), creator proposals and milestones (0023/0029/0040), BYO (0016), the client money library `app/src/lib/money.ts`, the client checkout `app/src/lib/payments.tsx`, the edge functions `create-payment`, `verify-payment`, `razorpay-webhook`, `process-refunds`, `release-payouts`, `provider-payout-account`, `_shared/*`, and all payment, refund, payout, transfer, reversal and receivable tables and RPCs. Coins are covered only where they change a payable or refundable amount. Invoices and receipts are left to WS9.

**Method.**
1. I built an index of the **latest** `create or replace function` per name across all 58 migrations. Later migrations override earlier ones, so every claim below cites the latest definition. Examples: `record_payment_paid` → `0029:167`, `_finalize_completion` → `0014:642`, `_create_payout` → `0016:67`, `_commission_bp` → `0043:14/48`, `claim_due_transfers` → `0058:1766`, `resolve_dispute` → `0021:1016`, `_cancellation_outcome` → `0029:323`, `demo_settle_payment` → `0030:736`.
2. I read each edge function in full and traced it into the SQL RPCs it calls.
3. I matched test names to features in `supabase/tests/*.mjs`, the Deno `*_test.ts` files and Jest `money.test.ts`. **Caveat:** some SQL suites load only early migrations. `migration.test.mjs` loads only `0001` plus `0007` and `0010` (`migration.test.mjs:9,47-48`). `fixed_booking.test.mjs` loads up to about `0019`. `cancellation_payouts.test.mjs` loads up to `0023`. A PASS from those files proves the **baseline** function body, not necessarily the latest override. Where that matters, this is noted.
4. CI evidence (read with `gh`):
   - Backend deploy run 44358292571: all 82 registered SQL checks passed (as briefed).
   - Run 44361095946: Deno tests passed (as briefed).
   - **Publish-app run 44365580862** ran `npx jest`: `PASS src/lib/__tests__/money.test.ts`, 27/27 suites and 246/246 tests.
   - **E2E run 44365580570 concluded `failure`** ("Screens: 157, failed steps: 7"). It also ran with `EXPO_PUBLIC_DEMO_PAYMENT=1` (`e2e-web.yml:25`), so it proves nothing about live Razorpay.
   - **`razorpay-check.yml`** is a manual diagnostic. It only (a) lists payment links with the keys and (b) creates one *Payment Link*. The latest run, 43729959915 (2026-11-15), shows `key mode: test … Razorpay status: 200 (credentials accepted)`, then `payment link failed: 429; code=RATE_LIMIT_EXCEEDED; description=test mode limit of 30 reached for payment_link`. Run 43729679731 passed step 1 only. **No CI step exercises Orders, Checkout, signature verification, capture, webhooks, refunds, Route transfers or RazorpayX payouts against Razorpay.** Every live-gateway path is therefore **BLOCKED** (or **DEMO ONLY** where a demo substitute exists).
5. Statuses use only this vocabulary: PASS, FAIL, PARTIAL, NOT IMPLEMENTED, DEMO ONLY, BLOCKED, NEEDS REAL USER VALIDATION, UNTESTED. "FAIL" is used where the code demonstrably produces a wrong financial result, even if no test exists yet. In those cases a test is proposed.
6. Indian GST, TDS and TCS questions are flagged **"requires professional tax/legal review"**. No legal conclusions are drawn.

## Findings

| ID | Title | Type | Severity | Gate | Evidence | Recommendation |
|---|---|---|---|---|---|---|
| WS6-01 | **Fixed packages, fixed recurring occurrences and creator proposals settle with 0% commission and 0 GST** | Technical defect / Business logic | P0 | Before accepting real payments | Fixed quote `subtotal_labour=0`, value in `subtotal_other` (`0019_fixed_package_booking.sql:346-351`; `0057_recurring_plans_v2.sql:990-997`). Proposal quote inserts `total` only, so `subtotal_labour` defaults to 0 (`0040_urgent_proposals.sql:349-352`, `0001:178`). Settlement commissionable = `q.subtotal_labour + q.subtotal_travel` (`0014_travel_requests.sql:659`) → `_create_payout(...,0,...)` → commission 0. Intended policy per `docs/07:204` (C4 commissionable subtotal) and `docs/07:387` (fixed 15/13/12%; proposal 8% capped ₹5,000). Client `money.ts:87` already counts `package/addon/per_unit/travel` as commissionable. No SQL test asserts fixed or proposal payout commission (grep: none in `fixed_booking`, `proposal_booking`, `recurring_plans` tests). The cancellation path *does* charge commission on provider compensation (`0021:926`), so a cancelled fixed job is commissioned but a completed one is not. | Owner decides the rates (doc 07 D1). Then implement `_commissionable(kind)` + `quotes.subtotal_commissionable`, set it in every quote writer, and make `_finalize_completion` use it with the per-archetype rate and proposal cap (WS6-T03). |
| WS6-02 | **Concurrent verify-payment + order.paid webhook can refund a valid payment** (home services, sessions, packs) | Technical defect | P0 | Before accepting real payments | `record_payment_paid` checks `exists(... razorpay_payment_id = p_payment_id)` **before** taking the row lock (`0029:185-188`). The second concurrent caller passes the check, blocks on `for update`, then sees `p.status='paid'` (READ COMMITTED re-read). It takes the "not owed" branch (`0029:225-231` scheduled, `0029:297-304` legacy): it overwrites `razorpay_payment_id`, calls `_queue_refund(p.id, p.amount)` and marks the payment `refund_pending`, while the booking stays confirmed. Same pattern in `record_session_payment_paid` (`0030:637-655`) and `record_pack_payment_paid` (`0022:566-583`). Both callers fire on every successful checkout (`verify-payment/index.ts:51`, `razorpay-webhook/index.ts:57`). Sports avoids this with `pg_advisory_xact_lock(hashtext(p_payment_id))` and a re-check (`0058:1415-1438`). | Port the sports pattern: advisory lock on the payment id, re-check `exists` after the lock, and treat `p.razorpay_payment_id = p_payment_id` as a duplicate (WS6-T01). Add a two-session concurrency test. |

### 1. Home-service visit — inspect & quote (TODAY correct)

- Specific fields: `visit_fee_paise` (M, credited into the quote), `labour_paise`, `parts_paise`, `other_paise`, `travel_paise`.
- Rule: `customer_payable = max(quote_total, visit_fee) + platform_fee`. Commissionable = labour + travel.
- **Sample** (doc 03 example, provider past free period, 12%):
  - Labour 150000 (₹1,500) + parts 65000 (₹650) → quote 215000 (₹2,150). Visit fee 19900 (₹199). Platform fee 2900 (₹29).
  - **Customer payable** = 215000 + 2900 = **217900 (₹2,179.00)**: 19900 at booking and 198000 balance.
  - **Commission** = round(150000×1200/10000) = **18000 (₹180.00)**.
  - **GST on commission** = round(18000×18/100) = **3240 (₹32.40)**.
